# M5.2.6 — ConversationContextBudget

## Status

automatically-accepted

## Scope

Remediate FINDING-007 (context budget semantics are inconsistent): unify history/knowledge budgeting onto one deterministic estimation unit and add an explicit reserved-output accounting, instead of mixing character length (`ContextBuilder`), word count (`ConversationContextService`) and per-chunk token count (knowledge engine) as separate, uncoordinated enforcement units.

## Implementation evidence

- New `ai_assistant/application/conversation_budget.py`: `estimate_tokens(text) -> int` (single shared word-count estimator, not a real tokenizer — a real tokenizer remains an explicitly out-of-scope "Later" item per the audit) and frozen `ConversationContextBudget(provider_context_window=8192, reserved_output_tokens=2048)` with a `max_input_tokens` property and validation (`reserved_output_tokens` must be non-negative and strictly less than `provider_context_window`).
- `ai_assistant/application/context.py`: `ContextBuilder._select_history` now uses `estimate_tokens(...)` for the system prompt, user input and every history message instead of raw `len()` character counts — the literal FINDING-007 fix.
- `ai_assistant/application/conversation_context.py`: `ConversationContextService` now takes a `budget: ConversationContextBudget` and enforces knowledge injection against `budget.max_input_tokens` (window minus reserve); its own `_token_count` helper delegates to the same shared `estimate_tokens`.
- `ai_assistant/bootstrap/config.py` / `container.py`: new `AI_ASSISTANT_RESERVED_OUTPUT_TOKENS` env var wired into a `ConversationContextBudget` constructed from `context_limit`/`reserved_output_tokens` and passed into `ConversationContextService` in `create_application`.
- Test rewrites: `tests/test_agent_runtime.py::test_context_builder_prefers_recent_history_within_budget` updated to word-count semantics (documented inline why); `tests/test_conversation_context.py` updated for the `budget=` constructor param plus two new tests proving the reserve is actually subtracted (`window=3/reserve=2` produces the same ceiling as `window=1/reserve=0`) and that an invalid reserve is rejected; `tests/test_cli_app.py::test_bootstrap_wires_context_limit` updated to pass a compatible `reserved_output_tokens=0` for its tiny `context_limit=123` fixture.

## Independent validation evidence (2026-08-28)

- **Test agent**: PASS on all 5 checks; explicitly verified the reserve-enforcement test proves subtraction (not just "some budget works"); full suite 547 passed/17 skipped.
- **Security reviewer**: PASS — budget change is scoped purely to conversational prompt assembly, does not touch `AI_ASSISTANT_MAX_READ_BYTES` or any `ToolPolicy`/`PathPolicy`/executor limit; 183-test security/tool-loop slice green.
- **Architecture reviewer**: PASS — layering test green, `estimate_tokens` is genuinely the one shared unit across all three enforcement points (grep confirmed no leftover raw `len()` character budgeting), ADR-024 unaffected. Recommends ADR-071 stay `Accepted` (not `Implemented`) since `ollama_num_ctx`/`num_predict` (M5.2.5) still has no code path coordinating it with this application-level budget — full ADR-071 coordination is not yet closed.

## Acceptance decision

M5.2.6 is **automatically-accepted**. ADR-071 remains `Accepted` (residual item tracked below).
