# M5.2.8 — Deterministic ToolLoopBudget and Controller (ADR-069)

## Status

automatically-accepted

## Scope

Remediate FINDING-001 (legitimate two-step tool workflows are rejected outright by the old hard one-round cap) and FINDING-004/005 (no deterministic, auditable ceiling on tool-round/tool-request/executor-operation counts) by replacing the ADR-024 single-round cap with a bounded, purely-numeric multi-round budget, without introducing any LLM-based judgment into the control flow. Implemented together with M5.2.9 (duplicate-call guard), M5.2.10 (progress guard), M5.2.11 (bounded multi-round chat loop) and M5.2.12 (final synthesis on exhaustion) as one cohesive change set, since all five share the same new module and the same rewritten `AgentRuntime` control flow. Full implementation evidence for all five milestones is recorded here; `M5.2.9.md` through `M5.2.12.md` are pointer files.

## Implementation evidence

- New `ai_assistant/application/tool_loop.py`: frozen `ToolLoopBudget(max_model_tool_rounds=3, max_tool_requests=5, max_executor_operations=8)` with `__post_init__` validation rejecting any non-positive field (`ValueError`, one message per field). No hardcoded numeric loop-control literals live anywhere else — the budget is the single source of truth for how many rounds/requests/executor operations a turn may spend.
- `ai_assistant/domain/tools.py`: `ToolExecutionResult` gained `executor_operations: int = 1`, validated non-negative in `__post_init__` (`InvalidToolCallError` otherwise). This lets a single tool call honestly report how much executor work it actually spent (1 for a direct outcome, 2–3 when the existing path-recovery retry logic from the earlier fix kicks in), so the loop's budget accounting reflects real work, not just call count.
- `ai_assistant/application/tool_coordinator.py`: `_resolve_path()` and `_attempt_recovery()` now return `tuple[ToolExecutionContext | None, int]` instead of just the context, so the coordinator threads the actual number of path-resolution attempts spent through to the final `ToolExecutionResult.executor_operations` (via `dataclasses.replace`). `_deny()` and `_deny_context()` accept an explicit `executor_operations` keyword (0 for an early denial before any resolution work, 1 for a denial after a completed resolution attempt).
- `AgentRuntime` (`ai_assistant/application/runtime.py`) gained a `tool_loop_budget: ToolLoopBudget = field(default_factory=ToolLoopBudget)` constructor field, defaulting the same numbers as the bare dataclass so existing callers get the new bounded behavior with zero config changes.
- `tests/test_tool_loop.py` (new): unit coverage for `ToolLoopBudget` validation (`test_tool_loop_budget_rejects_non_positive_limits`) plus fingerprinting and both guards (see M5.2.9/M5.2.10 below).
- `tests/test_tool_coordinator_recovery.py`: added `test_executor_operations_is_one_for_a_direct_success` and `test_executor_operations_is_zero_for_an_unknown_tool`; extended `test_successful_recovery_reports_metrics_without_extra_round` with `assert result.executor_operations == 3`.

## Independent validation evidence (2026-08-28)

Three independent `general-purpose` subagents reviewed the full Group C change set (M5.2.8–M5.2.12) together, since they land in the same files and are only meaningfully testable as one behavior:

- **Test agent**: PASS on all 5 checks. Manually traced the bounded loop end-to-end (budget exhaustion, duplicate rejection, progress-guard stop, final synthesis, path-recovery executor-operation accounting) and found no exploitable gap. One minor, explicitly non-blocking note: `max_executor_operations` is checked *between* rounds, not pre-empted *mid-call* — a single call whose internal path-recovery retries push the running total over budget can finish that round before the next check catches it. Not a correctness defect (the loop still terminates at the next boundary) and not required by any binding constraint; recorded here rather than silently dropped.
- **Security reviewer**: PASS on all 7 checks. Full security/tool-loop regression slice: 181 passed, 0 failed. Confirmed the new budget/guards make ToolPolicy/PathPolicy/confirmation/audit/path-recovery strictly harder to bypass (fewer executions succeed unconditionally now, not more), and that `ToolLoopBudget`/guard state never leaks into audit payloads beyond the existing sanitized fields. One pre-existing, non-regression note: `ConfirmationService` grant caching persists across rounds within a turn exactly as it did before this change — flagged for awareness, not a new issue introduced by M5.2.8–12.
- **Architecture reviewer**: PASS on all 6 checks. Confirmed both guards are structurally load-bearing (dedicated tests assert actual coordinator call counts, not just guard-unit behavior in isolation), confirmed no hardcoded loop-control literals exist outside `ToolLoopBudget`'s own defaults, and confirmed `ProgressGuard()`'s internal default of `max_consecutive_failures=2` is an acceptable *guard-parameter* default (analogous to any other constructor default), not the kind of hardcoded loop-control logic the binding constraints forbid. Flagged, as an actionable finding, that ADR-024 was left `Status: Implemented` with no `Superseded by:` despite ADR-069 already declaring `Supersedes: ADR-024` and the code no longer enforcing a hard single-round cap — recommended fixing this immediately (not deferring to phase closure), and separately recommended deferring ADR-069/070/071's `Accepted -> Implemented` promotion to full Phase 5.2 closure (M5.2.16), since ADR-070/071 are not yet fully satisfied end-to-end.

## Acceptance decision

M5.2.8 is **automatically-accepted**.

## Corrective action taken from review findings

Applied the architecture reviewer's ADR-024 finding immediately, as recommended: `docs/adr/ADR-024-bounded-single-tool-round-per-turn.md` now reads `Status: Superseded`, `Superseded by: ADR-069`; `docs/adr/README.md`'s ADR-024 index row updated to `Superseded (by ADR-069)`; `AGENTS.md`'s ADR-governance section updated to state ADR-024 is superseded rather than describing it as "the current one-round design." ADR-069/070/071 deliberately remain `Accepted` (not `Implemented`) per the reviewer's explicit recommendation to defer that promotion to M5.2.16.

## Residual item carried forward

The `max_executor_operations` inter-round (not mid-call) check noted by the test agent is accepted as-is: pre-empting mid-call would require interrupting an in-flight path-recovery retry sequence, which is out of scope for this milestone and not required by any FINDING or binding constraint. No follow-up milestone is created for it; it is documented here for the final closure audit (M5.2.16) to re-confirm as a known, bounded, non-regressing characteristic rather than an overlooked gap.
