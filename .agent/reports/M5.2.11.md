# M5.2.11 — Bounded Multi-Round Conversational Tool Loop

## Status

automatically-accepted

Implemented together with M5.2.8, M5.2.9, M5.2.10 and M5.2.12 (same change set, same files). Full implementation evidence, independent validation evidence and acceptance decision are recorded in `.agent/reports/M5.2.8.md` — this file exists only to give M5.2.11 its own report pointer in the roadmap table.

## Scope delivered

`ai_assistant/application/runtime.py`: `AgentRuntime._run_tool_loop()` replaces the old hard-capped `_respond_with_tool_round()`. It drives a `while True` loop bounded purely by `self.tool_loop_budget` (`max_model_tool_rounds`, `max_tool_requests`, `max_executor_operations`) plus the deterministic `DuplicateCallGuard`/`ProgressGuard` from M5.2.9/M5.2.10 — no hardcoded numeric loop-control literals. This is the direct fix for FINDING-001: a model that legitimately needs two or three distinct tool calls in sequence (e.g. `list_directory` then `read_file`) now completes the workflow within one turn instead of having its second, legitimate request rejected outright.

Every `ToolExecutionRequest` built during the loop (including rejected/duplicate/exhaustion cases) carries the turn's `interaction_id` (M5.2.7), and `executor_operations_used` is accumulated across rounds and checked against `tool_loop_budget.max_executor_operations` before each new round starts.

Test rewrites reflecting the new, correct behavior (the old assertions literally encoded the ADR-024 behavior this milestone replaces):

- `tests/test_agent_runtime.py::test_runtime_stops_once_tool_loop_budget_is_exhausted` (renamed from `test_runtime_stops_after_second_tool_request`): 4 distinct scripted tool calls, asserts exactly 3 execute before the 4th is rejected for budget exhaustion.
- `tests/test_agent_runtime.py::test_runtime_completes_list_directory_then_read_file_within_budget` (new): the literal FINDING-001 regression demo — a two-step legitimate workflow now completes in one turn.
- `tests/test_adversarial_security.py::test_runtime_rejects_tool_round_once_budget_exhausted` (renamed from `test_runtime_second_tool_round_is_not_executed`): 4 distinct `read_file` calls, asserts exactly 3 execute (`one.txt`, `two.txt`, `three.txt`) and the model receives a real synthesized answer, not a fixed rejection string.
- `tests/test_tool_diagnostics.py::test_runtime_logs_denied_error_timeout_and_round_limit`: the "limit" sub-case rewritten to 4 distinct `read_file` calls, asserting the diagnostic status sequence `["requested","executed"] * 3 + ["requested","rejected"]` with `round_index == 4` and `error.code == "tool_loop_budget_exhausted"`.
